> 核心承诺：用户提供账单，Skill 将其整理成可追溯、可修正的月度财务记录。全额退款不干扰消费面板和习惯分析，原始证据始终保留。

## 1. 背景与问题

用户的消费、退款、分期与还款记录分散在支付宝、微信、信用卡、花呗、京东白条等平台。用户可能只有账单列表截图，其中仅有交易名称、金额和时间，没有订单号或交易号，也未必知道如何导出标准文件。

直接把这些记录汇总，会遇到以下问题：

1. 同一消费同时出现在支付平台与信用卡账单中，容易重复计费。
2. 分期购买与后续还款容易被重复算作消费。
3. 全额退款后，原购买仍影响消费排行、习惯分析与预算建议。
4. 补充账单、跨月退款和人工修正之后，历史报告容易失去一致性。
5. 用户无法判断「确实没花钱」与「账单还没提供」的区别。
6. 通用 Agent 能理解截图，但仅靠提示词完成金额计算和账务关系维护不够稳定。
7. 用户希望通过自然语言完成日常操作，而不是维护 CSV、数据库或运行命令行。

### 1.1 当前基线与已知缺口

以下基于仓库 `1d982de` 和 2026-10-22 的审查记录；不是本 PRD 编写时重新执行的测试结论。

| 已有基础 | V1.1 需要补齐 |
| --- | --- |
| Skill 已置于仓库根目录，并提供两种宿主的安装说明 | 区分宿主调用方式，首次设置不误把代码仓库当作 Vault |
| 支付宝、微信和统一 CSV 的直接导入入口 | 不同导出文件之间的幂等性、来源溯源和完整输入校验 |
| 退款匹配与支付平台/信用卡去重的基本实现 | 人工决定不被覆盖、跨账户隔离、连续导入与导入顺序稳定 |
| SQLite、月报、Dashboard、待确认页和质量页 | 数据覆盖状态、操作回执、批次撤销、用户笔记保护 |

原有 21 项测试在上一轮审查中通过，但合成场景仍暴露了重叠账单重复计费、人工退款被改配、旧分析残留和手写备注丢失等问题。V1.1 以这些可复现问题为优先修复对象。

## 2. 产品定位与目标

### 2.1 一句话定位

面向普通个人用户的账单整理 Skill：通过自然语言接收多来源账单，用确定性代码维护账务事实，在 Obsidian 中输出可信、可解释、可持续维护的财务视图。

### 2.2 产品目标

- **算得可靠**：消费、退款、重复记录、还款与现金流遵循明确规则。
- **用得省心**：用户不必记住哪些文件导入过，不必填写内部 ID，不必手动执行 CLI。
- **改得放心**：人工修正不会被静默覆盖，撤销操作不会删除原始证据。
- **看得明白**：每个数字都有口径、来源和质量状态，未知值不伪装成零。
- **长期可维护**：跨月补账能修正历史结果，重建不会破坏用户笔记。

### 2.3 非目标

- 不开发独立记账 App、银行客户端或 Obsidian 社区插件。
- 不自动登录支付平台，不接银行 API，不抓取邮箱，不做无人值守同步。
- 不承诺覆盖所有银行及所有版本的专用账单格式。
- 不提供独立 OCR 服务；非结构化提取依赖宿主 Agent 的可用能力。
- 不做多币种换算、投资组合、税务申报或授信建议。
- 不提供自动还款、资金划转或账户登录功能。
- 不把自动判断的「必要/非必要」消费作为 V1.1 必备指标。

## 3. 用户与使用场景

### 3.1 主要用户

主要服务于本人管理个人财务、使用多个支付渠道的 Obsidian 用户。用户可能没有技术背景，也可能尚未建立财务目录或分类规则。

同一 Vault 可记录用户自己的多个账户；需要区分不同账户归属，但 V1.1 不扩展为多人协作、家庭共同记账或组织财务系统。

### 3.2 核心用户故事

| 编号 | 用户故事 | 期望结果 |
| --- | --- | --- |
| US-01 | 我第一次使用，什么都没配置 | 引导确认 Vault，建立最小可用目录，可先体验合成演示 |
| US-02 | 我把几个平台的账单或截图一起交给 Agent | 按来源整理、按自然月汇总，标出无法确认的部分 |
| US-03 | 我买了东西又全额退款，不希望它出现在消费面板 | 消费和退款退出消费统计及习惯分析，但可以查证来源 |
| US-04 | 截图没有订单号 | 系统利用可见证据匹配；有多个候选时让我选择 |
| US-05 | 我忘记导过哪些账单，又提交了一次 | 不重复计费，并告知新增与重复的数量 |
| US-06 | 这笔分类错了，我只想改这一笔 | 只修改指定交易，不能顺带更改整个商户的分类 |
| US-07 | 我后来补了上个月的退款 | 修正原消费月，更新受影响分析，并解释历史变化 |
| US-08 | 我想撤销刚才导错的一批账单 | 撤回该批次统计影响，保留原始记录和其他有效数据 |
| US-09 | 我只想看看这个月的情况 | 读取现有结果，告知是否过期，不重新导入或任意写入 |
| US-10 | 我在月报里写了自己的复盘 | 后续自动更新仍保留我的文字 |

| 需求 ID | 能力 | 优先级 | 本版边界 |

| FR-03 | 重复导入与跨来源去重 | P0 | 强证据合并，弱证据待确认 |

## 5. 输入支持边界

| 来源/形式 | V1.1 处理方式 | 不能默认假设的内容 |
| --- | --- | --- |
| 已识别的支付宝、微信个人对账 CSV | 脚本直接解析；验证表头、编码、金额与状态 | 文件扩展名正确、某一固定行就是表头 |
| 统一格式 CSV | 脚本校验并导入 | 数据有效或来自完整账单 |
| 花呗、白条、信用卡、京东金融等其他账单 | 归档后由 Agent 按统一模型提取；能确定的内容再入账 | 已存在所有平台专用解析器 |
| XLSX、文本 PDF、HTML、邮件导出文件 | 使用宿主现有能力提取并保留来源定位 | 必有可用提取工具；失败时应说明替代格式 |
| 单张/连续账单截图 | 仅提取可见事实；保留图像、顺序与交易位置 | 有订单号、完整账期、看不清的金额和被截断的行 |
| 待还款/账单汇总截图 | 作为带截止日期的负债快照，不生成虚构消费 | 待还、应还、最低还款和余额是同一指标 |
| 余额宝、零钱通相关记录 | 区分购买支付、账户内部移动、申赎和收益 | 所有转出都是消费，所有收入都是工资 |
| 加密文件或压缩包 | 提示用户本地解密/解压后再提供 | 可以索取密码或自动登录平台 |
| 非 CNY 数据 | 明确提示暂不支持，不进入人民币合计 | 可忽略币种直接相加 |

直接解析支持必须按实际格式识别，不能只用平台名称承诺兼容。一个不支持的文件不阻止其他独立文件完成处理，但回执必须列出失败项和原因。

## 6. 产品交互与主流程

### 6.1 意图入口

Skill 根据请求执行最小必要流程，不把每个请求都解释为重新导入。

| 用户说法 | 执行意图 | 写入边界 |
| --- | --- | --- |
| “第一次使用，帮我设置” | 设置与环境检查 | 目标确认后初始化；演示与真实账本隔离 |
| “把这些账单加进去” | 导入、核对、更新受影响报告 | 仅指定来源和目标 Vault |
| “处理一下待确认” | 展示候选、记录用户决定 | 确认后更新相关关系与报告 |
| “这笔改成学习” | 单笔分类修正 | 默认只改这一笔；扩大范围需明确 |
| “看看这个月” | 读取和解释 | 默认只读；发现过期先说明 |
| “撤销上次导入” | 定位批次、说明影响、撤销 | 目标存在歧义时先确认 |

### 6.2 首次使用

1. 识别当前目录是否为用户希望写入的 Vault；不能因存在 `SKILL.md` 就视为 Vault。
2. 目标不明确时询问路径；目录不存在时确认是否创建。不得静默建立另一个仓库或 Vault。
3. 检查 Python、脚本资源与写入权限；给出具体解决方式，不要求关闭安全保护。
4. 简要说明云端处理、未加密文件及同步风险。
5. 使用默认分类即可开始；仅在关系判断确有需要时询问账户归属。
6. 可选创建独立的合成演示，不能写进已有真实账本。
7. 初始化后展示首页、下一步提示及已保存配置；之后不反复询问已明确的信息。

### 6.3 导入主流程

```text
接收指定文件 → 确认目标与来源 → 原始归档 → 提取/校验
    → 去重与退款关联 → 已确认部分入账 + 不确定部分待确认
    → 更新受影响月份与面板 → 更新/标记分析状态 → 输出操作回执
```

识别失败、解析失败与成功入账必须是不同状态。归档成功不代表账务导入成功。截图提取需要展示不确定字段，不能通过补造信息让流程继续。

### 6.4 退款复核交互

示例仅使用虚构数据：

> 这笔 199 元退款有两个可能的购买记录：
>
> A：7 月 10 日，示例商城，耳机，199 元。
>
> B：7 月 18 日，示例商城，配件，199 元。
>
> 请回复 A、B 或“暂不确定”。可以查看对应原始记录。

系统内部将当前候选映射为稳定交易标识。候选发生变化时必须重新展示，不能把用户对旧列表的“A”应用到新列表。暂不确定不会阻止其他已确认记录生成报告。

### 6.5 操作回执

每次写操作说明：处理的文件/批次、成功/失败项、新增交易、重复记录、退款变化、待确认数量、受影响月份、金额变化和产物路径。数字由处理器提供，Agent 不自行估算。

```text
示例回执：
新增交易：23 笔
重复记录：8 笔，未重复计入
确认退款：2 笔
历史修正：7 月净消费减少 199 元
待你确认：1 项
查看：月报 / 待确认 / 本次导入记录
```

## 7. 核心账务规则

### 7.1 三个视角必须分开

| 视角 | 回答的问题 | 计入原则 |
| --- | --- | --- |
| 消费 | 买了什么，最终保留了多少消费？ | 按购买月计算规范购买金额减已确认关联退款 |
| 现金流 | 什么时候实际付出或收到钱？ | 仅依据实际结算证据；支付与退款分别保留 |
| 负债 | 借贷消费、偿还和剩余待还有多少？ | 借贷事件与有截止日期的快照分别展示，不互相冒充 |

消费分析使用「净消费」；手续费与利息单列为金融成本，不能隐藏在还款本金中。借贷购买计一次消费，后续本金还款不再产生消费。

现金流汇总必须声明覆盖账户与已识别范围，不能称为用户全部现金流。本人账户间移动不计新增消费，也不在合并账户视图重复制造收入/支出；必要时保留账户层面的资金移动记录。投资申赎标为资产转换，不作为日常消费。对外转账若用途未知，应待确认，不能直接按内部转账排除。

「新增借贷消费」不等于「月末负债余额」。跨月退款可以修正购买月净消费，但债务冲减发生在哪天、月末还欠多少，必须依据相应事件或快照；不能把后来发生的退款当作过去已清偿的证据。

### 7.2 退款规则（产品核心）

1. **全额退款**：购买与退款均退出消费明细、分类/商户排行、消费次数、小额消费指标和习惯分析；原始来源、关联依据及有证据的现金事件保留。
2. **部分退款**：购买按剩余净额展示；累计确认退款不能超过购买金额。
3. **跨月退款**：修正购买月净消费，并在回执解释历史变化；现金到账只计实际到账月。
4. **多笔退款**：允许同一购买对应多笔退款；每个退款事件只能计算一次。
5. **退款先到**：没有原购买时保留待确认，后续补充账单再匹配；不得虚构原购买，也不算普通收入。
6. **无订单号**：在账户/平台关系明确的前提下，结合金额、时间、商户和支付方式等可见证据。仅唯一且证据充分的候选可自动关联；不以模型自报的置信度替代证据。
7. **多候选或冲突**：保留待确认，不能因为日期最近就选第一笔；后续新证据不得静默覆盖人工决定。
8. **信用支付退款**：区分已证实到账、仅冲减债务与结算未知。仅有额度恢复/待还减少不能产生现金退款流入。
9. **退款状态不等于退款事件**：原消费行出现“已退款”等文字时，保留该状态；不能把原金额直接当作新退款再计一次。
10. **人工决定可撤销**：撤销关联保留历史，并防止下一次自动匹配立刻恢复已被用户否定的关系。

退款成功/购买日期只显示日期时，按来源精度判断，不补造时分秒。无法证明时间或金额关系时进入复核。

### 7.3 去重与幂等

- 同一文件重复提交：不新增有效消费，不改变已确认关系。
- 不同文件中，同平台、同账户的可信交易 ID 相同：同一交易计一次，所有来源保留；同 ID 内容冲突时待确认。
- 支付平台与信用卡：只在支付链路和账户关系可验证、候选唯一时合并为一个消费事件。
- 没有 ID 的相同商户/金额：默认不足以证明重复。截图视觉重叠只有在能证明是同一可见记录时才去掉重复观测。
- 可疑重复暂不合并，保留来源口径暂定值，并说明可能高估；不能把不确定数值标为最终合计。
- 相同有效输入与相同人工决定，不同导入顺序应产生相同统计结果；重复运行不应新增无意义的待确认项。

### 7.4 分类与人工优先级

优先级为：单笔人工覆盖 > 用户授权的分类规则 > 自动分类 > 待分类。

三种操作必须区别：

| 用户选择 | 作用范围 |
| --- | --- |
| 只改这一笔 | 只修改指定规范交易；其他来源副本展示一致 |
| 以后这个商户这样分类 | 自规则生效后新发生的交易；补录的旧交易不因导入时间较晚而被误改 |
| 同时修正历史 | 明确说明影响范围，重分类符合规则且无单笔人工覆盖的历史交易 |

商户名称不足以判断用途时保留待分类。不能将“京东”“淘宝”等综合平台的全部交易自动视为数码、非必要消费或其他单一用途。

### 7.5 金额、时间与质量

- 金额按整数分或 Decimal 计算，不使用二进制浮点累计账务金额。
- 保留原始符号和展示方式；标准化按平台规则转换。不能对所有金额取绝对值来掩盖方向错误。
- 非有限金额、无法解析日期、非法枚举和不支持币种不能进入有效总账。
- 按自然月统计消费；入账日和账单周期用于账单核对，不能用账单月份替代购买月份。
- 未确认用途的交易保留记录并显示待确认影响，不强制归为消费或收入。
- 退款流入不算普通收入；收益与工资不混同；失败/关闭交易不算成功消费。

## 8. 数据质量与信任状态

不能只用一个“已完成”标签表示所有质量状态，至少分别维护：

| 状态维度 | 取值/展示 | 判定依据 |
| --- | --- | --- |
| 来源覆盖 | 完整 / 部分 / 未知 | 来源平台、账户、起止日期和完整性证据；截图默认部分 |
| 金额核对 | 未核对 / 同口径相符 / 存在差异 | 有来源汇总及对应口径才能计算差额 |
| 人工复核 | 无待确认 / 有待确认 | 包含退款、重复、类型、用途、来源冲突等，不仅统计退款 |
| 分析状态 | 待生成 / 当前有效 / 已过期 / 生成失败 | 分析使用的数据版本与最新有效输入是否一致 |
| 产物状态 | 已更新 / 待重建 / 生成失败 | 总账变更与报告是否同步 |

“原始行数等于标准化行数”不等于账单对平；不同平台的原始总额不能直接相加作为去重后总额的核对基准。只有原始汇总存在且口径一致时才能显示金额差额。

待确认金额表示涉及的不确定记录规模，不保证等于最终修正额；同一交易有多个问题时不能重复累计该金额。存在候选重复时，可以另外显示可能重复的金额，不输出没有计算依据的精确影响区间。

## 9. Obsidian 信息架构与页面要求

### 9.1 目标产物

以下是目标结构；新增页面属于 V1.1 需求，不代表当前全部存在。实际名称可在不破坏入口和可追溯性的前提下调整。

```text
Finance/
├── Dashboard.md                 总览、数据状态、待办和入口
├── Raw/<source>/                不可变原始文件
├── Data/                        规范总账、配置、分析输入、操作记录
├── Months/YYYY-MM.md            月报
├── Accounts/                    带截止日期的账户/负债摘要
├── Reviews/
│   ├── 待确认交易.md
│   ├── 数据质量报告.md
│   └── 退款核对.md
├── Imports/                     导入回执与撤销状态
├── Backups/                     升级前及必要的页面备份
└── Finance.base                 可选月报索引
```

SQLite 是规范数据源；修改展示中的计算金额不会自动改变总账。页面需清楚区分自动区域和用户笔记区域，提供自然语言修正入口。

### 9.2 Dashboard

按用户阅读顺序呈现：

1. **数据状态**：最新数据月份、覆盖日期/账户、最近更新时间、待确认数量及涉及金额、分析是否有效。
2. **核心指标**：已识别净消费、已确认现金支出、退款实际流入、债务还款、借贷消费；附口径与不完整标记。
3. **消费构成**：分类金额与占比、主要商户；全额退款不出现。
4. **需要处理的事**：待确认、缺失资料、过期分析，按影响和可处理性排序。
5. **负债快照**：账户、截止日期、剩余待还、本期应还、来源给出的还款日；缺失值明确显示未知。
6. **本月发现与建议**：有效分析摘要；没有足够数据时说明限制。
7. **历史入口**：月报列表、可比月份趋势表、退款核对、数据质量和导入记录。

空状态必须有用：没有交易显示“尚未导入账单”，没有负债资料显示“尚未提供”，不能据此显示用户零消费/零负债。最新账单为 7 月时，标题应标明“最新数据：7 月”，不能在 10 月仍称其为本月。

### 9.3 月报

每份月报包括：口径与覆盖状态、核心指标、净消费明细、分类/商户汇总、消费与现金流差异解释、金融成本、有效分析、最多三条建议、待确认/来源入口、更新时间与用户笔记区。

不要求每笔交易生成一个 Markdown 文件；月报和复核页应提供足以查证的交易标识及来源链接，避免大量笔记影响使用体验。

### 9.4 退款核对页

面向查证，不是消费榜单。展示原购买、退款日期/金额、匹配依据、人工/自动状态、净额、现金结算状态及原始依据。允许全额退款出现在此页，不得再次流入消费分析输入。

### 9.5 用户内容保护

- 重建仅替换受管理内容，保留用户笔记及非产品所有的 Properties。
- 旧版页面无法可靠识别生成边界时先备份并保留，不猜测覆盖范围。
- 自动区标记损坏或发生并发编辑时停止覆盖并说明解决方式。
- 数据未变化时保留有效分析；变化后旧分析保留为历史，不作为当前结论展示。

## 10. 消费分析与建议

### 10.1 分工

| 角色 | 职责 | 不应承担的工作 |
| --- | --- | --- |
| Agent | 理解输入、解释疑点、组织交互、撰写有依据的分析 | 凭直觉计算总额、虚构字段、强配模糊退款 |
| Python 处理器 | 校验、计算、关系维护、状态和回执、生成确定性指标 | 自行给用户贴消费动机或财务状况标签 |
| Obsidian | 展示、导航、保留个人复盘 | 充当唯一且不可恢复的账务事实来源 |
| 用户 | 明确账户归属、确认歧义、选择修正范围 | 记住数据库 ID、手动维护重复账单清单 |

### 10.2 分析内容

- 提供 2–4 条有数据支持的发现；不足以得出发现时可以少写或不写。
- 支持分类、商户、小额消费等描述；比较趋势必须覆盖范围可比。
- 每条结论包含对应金额、次数、占比或比较依据，可回到计算输入。
- 最多三条建议，指向可控制的行动或复核事项；没有用户预算时，不把任意目标金额说成“合理预算”。
- 不推断成瘾、健康、财务困境、消费动机或道德评价。
- 不根据账单中没有使用记录就判断订阅未使用。
- 不将全额退款商品计入习惯，不把还款本金当消费增长。

### 10.3 分析失效

分析绑定其输入版本。退款、去重、分类或覆盖状态发生有效变化后，相关月份分析标为过期；仅导入重复文件且账务输入未变时不应无故失效。

如果 Agent 无法生成新分析，账务与报告可先更新，但必须显示“分析待更新/生成失败”；不能因此继续展示过时建议为有效结果。保护旧文与保护用户备注是两件事，应分别处理。

## 11. 修正、撤销与异常处理

### 11.1 批次撤销

撤销表示停用指定批次的账务贡献，而不是删除文件或清空总账。

- 撤销前明确批次、来源和预计受影响月份；有歧义时必须确认。
- 其他有效批次仍提供同一交易依据时，该交易仍然有效。
- 撤销退款批次后，依赖该退款的净消费需要恢复并重新评估分析。
- 人工决定依赖被撤回记录时保留历史并标为当前不可应用，不任意转移到另一笔交易。
- 重复撤销同一批次不继续改变金额。
- 重新提交已撤销的相同文件时，提示其历史状态并确认是否重新纳入，不能无声恢复。

### 11.2 异常与恢复矩阵

| 异常 | 用户可见行为 | 数据要求 |
| --- | --- | --- |
| 文件不存在、加密或格式不支持 | 指出具体文件和替代方式 | 不伪报导入成功 |
| 某行金额/日期无效 | 指出行/位置及问题 | 该文件批次不部分提交有效总账；已归档原件保留 |
| 可解析但用途/类型不确定 | 进入待确认，并显示影响 | 其他有效记录正常处理 |
| 多个退款/重复候选 | 展示候选和原始依据 | 不静默选择 |
| 数据库升级失败 | 明确失败与恢复位置 | 保留可恢复的旧库 |
| 总账已更新但页面生成失败 | 显示“待重建”，提供重试方式 | 不撤销已成功账务，也不称全部完成 |
| AI 分析失败 | 保留有效数字和失败状态 | 不用旧分析冒充新结果 |
| 用户修改了配置或笔记 | 保留修改，遇冲突说明 | 不静默覆盖或恢复默认值 |
| 目标目录无写权限 | 提示授权指定目录或更换位置 | 不绕过权限、不写入其他 Vault |

## 12. 逻辑数据对象

本节约束产品语义，不规定具体数据库表名。

| 对象 | 关键内容 | 约束 |
| --- | --- | --- |
| 来源文件 | 文件哈希、来源、归档位置、覆盖范围 | 原件不改写；文件名不作为唯一身份 |
| 来源观测 | 原始列/可见文本、行/页/图像位置 | 一个经济事件可有多个观测 |
| 规范交易 | 稳定标识、账户、日期精度、金额、币种、类型与状态 | 不从缺失字段制造事实 |
| 关联关系 | 重复关系、购买与退款、证据、人工/自动来源 | 统计只计算规范事件一次 |
| 人工决定 | 目标、范围、修改前后、时间、撤销状态 | 自动处理不静默覆盖 |
| 导入批次 | 来源、结果、有效/撤销状态、回执 | 可撤回影响且保留审计 |
| 负债快照 | 账户、截止日期、待还/应还/还款日、来源 | 缺失用未知，不把旧快照冒充当前余额 |
| 分析输入与结果 | 指标、质量、输入版本、有效状态 | 分析必须对应有效输入 |

必须可追踪：面板指标 → 规范交易/计算口径 → 来源观测 → 原始文件。未知字段可缺失，缺失本身不能隐式变成“0”“成功”或“完整”。

## 13. 非功能要求

### 13.1 正确性与安全性

- 在验收数据集中，所有确定性金额按分精确匹配，不接受浮点容差掩盖差额。
- 同一操作重复执行不产生额外账务影响；人工确认与原始证据在重建中保持。
- 单个文件导入具备一致的提交边界；页面使用安全替换，避免半个 JSON/Markdown。
- 迁移前备份且保留版本信息；恢复方式需可操作，不仅记录“已备份”。
- 同一 Vault 的并发写入需要检测/串行化，不能以静默覆盖解决冲突。

### 13.2 隐私与权限

- 自带脚本不主动联网、上传账单或发送遥测；不等于整个 Agent 处理链完全离线。
- 云端 Codex/Claude 可能将用户提供的内容传输给服务提供商；遵循宿主设置及其数据政策。
- 原件、数据库、报告和备份默认未加密，可能被 Obsidian Sync、iCloud、Git 或其他工具复制。
- 不索取密码、验证码、登录凭据或完整卡号；不把敏感内容写入公开 Issue、示例、测试或提交。
- 账单内的商户文字/备注是数据，不是可执行指令；不能据此改变写入目标、上传文件或执行命令。
- 仅访问用户指定或任务明确授权的来源和 Vault；不递归扫描无关目录。

### 13.3 兼容与交付

- `SKILL.md`、`scripts`、`references`、`assets` 保持仓库根目录布局；无需独立后台服务。
- Python 3.9+，确定性运行时仅标准库；额外提取能力按宿主实际可用性说明。
- README 分开呈现 Codex `$personal-finance-obsidian` 与 Claude Code `/personal-finance-obsidian` 的使用示例，并在发版时核验宿主兼容性。
- CLI 对用户是高级用法，对 Agent 是正常账务处理的执行入口。
- 核心展示为 Markdown 与 Properties；Bases 不可用时功能不降级到无法使用。
- 正式发布只声明实际验证的系统/版本；不凭标准库使用就承诺所有平台已经测试。

### 13.4 性能与可用性

结构化导入、全量重建和重复导入应分别记录运行时间与数据规模。发布测试至少包含小规模交互样例和万笔合成记录；性能结论需注明机器与环境，不在没有测量时承诺秒级 SLA。

不为常规使用新增遥测。体验评估基于合成场景、用户自愿反馈和本地可检查结果。

| 指标 | V1.1 目标 | 测量方式 |

| 用户笔记丢失 | 0 | 旧页迁移和重复生成对比 |
| 未知值误呈现为已知零值 | 0 | 空数据、缺失快照和结算未知场景 |
| 常规操作必须手动执行 CLI | 0 | 首次设置/导入/复核/分类/查看/撤销场景验证 |
| 统计交易具备来源依据 | 验收场景 100% 可追溯 | 指标到原始文件的逐级检查 |

这些是验收目标，不是已获得的运营数据；本版不新增行为追踪服务。

### 15.2 交付顺序

1. **可靠账务**：导入身份、去重、退款、状态校验、来源追溯。
2. **可修正与恢复**：人工决定、分类范围、批次回执、撤销与备份。
3. **可信展示**：笔记保护、分析失效、数据质量、Dashboard 和月报。
4. **日常体验**：Skill 意图入口、首次设置、演示、自然语言复核及安装说明。
5. **发布验证**：连续使用流程、旧数据升级、宿主兼容和可选 Bases。

具体开发拆分和测试步骤见实施计划；本 PRD 不承诺尚未估算的交付日期。

## 16. 风险、产品默认值与待确认项

### 16.1 主要风险

| 风险 | 应对 |
| --- | --- |
| 平台导出格式变化或截图信息不足 | 内容识别、显式失败、保留来源、不伪造完整性 |
| 无 ID 匹配误判 | 候选唯一和多项证据约束，弱证据转人工 |
| 所有来源都不完整，仍给出精确分析 | 每层携带覆盖状态，只分析已知范围 |
| 原始资料被同步到其他设备或云端 | 首次说明隐私边界，不自行改变同步设置 |
| 旧数据升级、人工修正与撤销关系复杂 | 版本迁移、备份、来源依赖和连续使用回归 |
| Skill 指令与脚本实际能力不一致 | 指令用真实命令/产物验收，不仅检查文字或文件是否存在 |

### 16.2 本 PRD 的补充默认值

以下细节是在已确认方向之上为验收补全的产品默认值，尚不是用户逐条确认的决定：

- 未来商户规则按交易发生时间生效，而非导入时间；历史调整必须显式选择。
- 单文件批次出现硬校验错误时不部分提交；多个独立文件可分别成功或失败。
- 已撤销文件重新导入需要明确重新纳入，不能自动恢复。
- 可疑重复暂不合并，现有来源统计标为暂定并提示可能高估。
- 财务汇总限定在已覆盖账户范围，投资申赎单列为资产转换；是否在首页现金流中展示这类资金移动，需进一步确定呈现方式。

### 16.3 实施前/发布前需明确

1. 首个正式验证平台与 Codex/Claude Code 版本范围；不能承诺未测试平台。
2. 大数据性能基线与可接受等待时间，在万笔合成数据上测量后确定。
3. 备份保留策略；未确定前不自动删除旧备份。
4. 来源没有汇总值时的对账体验：保持未核对，不以推算总额代替来源证据。

这些待确认项不改变全额退款隐藏、原始记录保留、人工决定优先及不确定结果可见等核心要求。
