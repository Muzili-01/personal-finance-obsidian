# 日常交互

先定位 Skill 目录（含 SKILL.md、scripts 和 assets），再确定目标 Vault。当前是代码仓库时不能静默初始化 Finance；没有明确目标只问路径。目标已有配置时复用，不反复询问。doctor 不写入；init 是明确设置操作，生成空首页。

## 首次与演示

用户可提供已有 Vault 或明确创建新目录。先 doctor，核对 Python 3.9+、资源与目标写权限。用简短说明交代云端 Agent、未加密存储和同步复制，再在已授权目标 init。没有 .obsidian 标记不自动否定用户明确指定的目标。合成 demo 只接受全新目录；不得混入已有账本。不要安装到其他目录或更改宿主设置。

## 复核

1. 调用 review --json，保留 review_id、transaction_id、snapshot、candidates 和 sources。
2. 展示可读的日期、商户、金额、账户与原始来源，例如 A/B/暂不确定。不要让用户填 ID。
3. 收到答案后再次读取 review，确认该 snapshot 和候选身份仍一致；任何变化重新展示，不能把旧“A”套到新列表。
4. 退款选择用 link-refund，同时传 snapshot；类型、方向、现金/债务结算、内部/对外转账用 resolve-review。多项问题可分别确认，禁止用“成功”填补原始缺失事实。
5. 无 ID 疑似重复可在用户确认后 resolve-review duplicate_of；不确定就保留暂定。来源同 ID 内容冲突时展示各来源值；用户明确选择后以 resolve-review 的 raw_id 记录来源选择。选中来源批次停用后，决定保留但当前不应用，不转移到另一个来源。
6. 构建后解释改变及仍待确认的问题。解除退款用 unlink-refund；分类或字段/重复修正用 undo-decision；保留决定历史。

人工复核不是自动批准。用户未作选择，或候选变化，不能写决定。自动匹配不会覆盖人工决定；有新冲突时会重新显示。

## 分类

“这笔改成学习”默认仅 transaction。未来商户规则 merchant-future 以交易发生时间生效，补录旧交易不套用；修正历史 merchant-all 明确改变同商户未单笔覆盖的历史记录。修改配置后，用户明确要历史重分类才 reclassify。单笔人工覆盖始终优先。

## 查看

report 是只读：显示已存在报告、artifact_status 和分析状态。pending/failed 的页面可能滞后于总账，先说明；用户只要求查看时不自动重建。也可直接读取 Dashboard/月报与上下文，但不能把旧分析当有效。不要运行 init/import/build-all。

## 撤销

从 Imports/导入记录.md 与 JSON 回执定位指定批次；“上次”存在歧义就先展示文件名、时间、月份供选择。说明影响后 undo-import，再重建。重复撤销无额外影响；已撤销文件再导入必须明确重新纳入，才能传 --reactivate。其他批次仍支持的交易继续计入。

## 失败

多个文件独立成功/失败，不因一个不支持的文件停止全部工作。坏行明确位置，该文件不部分入账。总账成功但页面失败：保留回执，说明待重建，修复后 build-all；不要重新导入来“恢复”。并发锁存在时不绕过，不删除仍活跃进程的锁。

原生平台 CSV 的账户归属若未建立且存在多账户可能，先确认该来源的账户标签；使用 --account-name，并从已保存批次复用，不按文件名猜测。规范 CSV 则保留行内账户身份。
